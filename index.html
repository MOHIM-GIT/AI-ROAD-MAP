One-time setup

You need Python 3.10 or newer. Create a folder, make a virtual environment (an isolated box for this project's packages), and install what the book uses.

How it works

The first command, python -m venv .venv, creates a hidden folder holding a private interpreter and its own package directory, so two projects can depend on different versions of the same library without conflict. Activating it puts that interpreter first on your PATH, which is why (.venv) appears in your prompt.

pip install then fetches the packages. openai is the official client, langchain and langchain-openai provide the application framework and its OpenAI bridge, python-dotenv loads secrets from a file, numpy and scikit-learn cover numerical and classical ML work, and tiktoken counts tokens. Once the project works, run pip freeze > requirements.txt to record exact versions so it can be rebuilt on another machine.

AI and ML basics

Before LLMs, learn the idea underneath all of it: a model learns patterns from data, then predicts on data it has never seen.

  • Training vs testing
  • scikit-learn
  • Overfitting

The three kinds of learning

Supervised

Learn from answers

You give examples with correct labels. Predict house prices, spot spam.

Unsupervised

Find structure

No labels. The model groups similar things, like customer segments.

Reinforcement

Learn from reward

An agent tries actions and gets scores. Game players, robots, and parts of LLM training.

Your first model

This program trains a model to tell three flower species apart from four measurements, then checks itself on flowers it never saw during training.

How it works

The scikit-learn loader returns the data as two arrays: X holds the features, four measurements per flower, and y holds the labels, the species encoded as 0, 1 or 2. train_test_split shuffles the rows and keeps 20 percent aside, and fixing random_state makes the shuffle reproducible so that two runs can be compared fairly.

A random forest is an ensemble of many decision trees, each trained on a random sample of rows and features, whose votes are combined. The averaging is what makes it far harder to overfit than a single tree. Calling fit is training, predict is inference on rows the model has never seen, and accuracy_score is the fraction of predictions that match the true labels. The discipline to remember is the split: any number you report must come from data the model did not learn from.

Key idea

Always test on data the model did not train on. A model that scores 100% on its own training data may have memorised it. That failure is called overfitting.

Neural networks in one minute

A neural network is layers of small maths units. Each unit multiplies its inputs by weights, adds them up, and passes the result on. Training adjusts millions of weights until predictions improve. A loss function measures how wrong the model is, and gradient descent nudges the weights to lower that loss. LLMs are neural networks with billions of weights.

How learning actually works: gradient descent

Training is optimisation. A model has parameters, a loss function scores how wrong it is, and gradient descent repeatedly moves every parameter a small step in the direction that reduces the loss. The derivative of the loss with respect to a parameter, called the gradient, tells you which direction that is. In a deep network the gradients of all layers are computed efficiently by backpropagation, which applies the chain rule from the output back to the input. The program below does the whole procedure for the simplest possible model, a straight line, so that every step is visible.

How it works

The data is generated from a known line plus noise, so you can check what the model ought to find. The model is w * X + b and the loss is the mean squared error. Differentiating that loss gives 2 * mean(error * X) for the weight and 2 * mean(error) for the bias, which are the two grad lines, and this is backpropagation in its smallest form. The update subtracts each gradient scaled by the learning rate.

Run it and the loss falls from about 540 to about 0.94, while w and b settle near 3 and 5, with the remaining loss being the noise you added. A learning rate that is too large overshoots and diverges, and one that is too small crawls, so try 0.1 and 0.0001 to see both failures. Neural networks do exactly this with millions or billions of parameters, using an optimiser such as Adam, which adapts the step size per parameter, in place of the plain update.

Evaluate like an engineer

Accuracy alone is a weak report card. If 98 percent of emails are not spam, a model that never flags anything scores 98 percent and is useless. Serious evaluation uses several tools: precision and recall for imbalanced classes, cross-validation to measure variance, and a pipeline that keeps preprocessing inside the training fold.

How it works

Five-fold cross-validation splits the data into five parts, trains on four, tests on the fifth, and rotates through all five. You get every score, so you see the variance as well as the average instead of trusting one lucky split. Wrapping the scaler and the classifier in a pipeline is not cosmetic: the scaler is re-fitted inside each training fold, so no statistics from the test fold leak into training. That kind of data leakage is the most common reason a model looks excellent in a notebook and fails in production.

F1 is the harmonic mean of precision, the fraction of positive predictions that were right, and recall, the fraction of real positives that were found. It is the better headline whenever classes are imbalanced, because accuracy can look high for a model that never predicts the rare class.

How LLMs work

A large language model reads text as tokens and predicts the next token, over and over. That one trick powers chat, code and agents.

  • Tokens
  • Context window
  • Temperature

Tokens: how the model sees text

Models do not read letters or words. They read tokens, which are chunks of text turned into numbers. You pay per token and the context window is measured in tokens, so counting them is a daily skill.

How it works

tiktoken.get_encoding loads the tokenizer, a vocabulary built with byte-pair encoding, an algorithm that starts from bytes and repeatedly merges the most frequent neighbouring pairs into new tokens. That is why a common word becomes one token while rare words, names and code identifiers split into several pieces.

encode returns a list of integers, which is the real input the network receives, and the length of that list is what you are billed for and what counts against the context window. English averages about four characters per token, but text in other scripts such as Bengali or Hindi often needs more tokens for the same meaning, which makes such prompts costlier. decode reverses the mapping exactly, so tokenization is a lossless code. Different model families use different encodings, so always count with the one that matches your model.

Temperature: controlling randomness

For each next token the model produces scores. Temperature rescales those scores before choosing. Low temperature makes the top choice dominate. High temperature gives other choices a real chance. This tiny program shows it with numbers.

How it works

The list scores stands in for the raw outputs, called logits, that a network produces for each candidate next token. Dividing by the temperature before the softmax changes how sharp the distribution is. Below 1 the gaps widen and the top word dominates, above 1 they shrink and unlikely words get a real chance.

Subtracting the maximum before exponentiating changes nothing mathematically but prevents numeric overflow, a standard stability trick. Softmax then turns the scores into probabilities that sum to one. Run it and you will see cat take almost everything at 0.2 while the three words converge at 2.0. A temperature of 0 is the limiting case where the highest score always wins, though hosted models can still vary slightly between runs.

Four facts that explain most LLM behaviour

  • Context window. The model only sees what is in the current conversation, up to a token limit. It has no memory between calls unless you send the history again.
  • Hallucination. The model produces likely text, not verified facts. It can sound sure and be wrong. Fix it by giving sources (RAG, chapter 8) and checking outputs.
  • Training vs prompting. Pre-training teaches language. Fine-tuning adjusts behaviour. Prompting and RAG change what the model sees at run time and are cheaper to try first.
  • Cost. You pay for input and output tokens. Long prompts and long histories cost more.

Inside the transformer: attention

Each token is a vector. A transformer layer projects every token into three vectors: a query (what am I looking for), a key (what do I contain) and a value (what will I pass on). The attention weight between two tokens is the softmax of the scaled dot product of one token's query with the other's key, and the output for a token is the weighted sum of the values. Stack many such layers, each with several attention heads running in parallel plus a feed-forward network, and you have the architecture behind every modern LLM.

How it works

The function computes Q @ K.T, a matrix scoring every query against every key, and divides by the square root of the dimension so that scores do not grow with size and push the softmax into regions where gradients vanish. The causal mask sets scores for future positions to a huge negative number, so after the softmax their weight is zero. That mask is what lets a language model learn to predict the next token using only the past.

Each row of the printed weight matrix sums to one and shows how much a token draws from each earlier token, with zeros above the diagonal. The matrix is T by T, so attention cost grows with the square of the sequence length, which is why long contexts are expensive. Attention alone has no sense of order, so real models add positional information, such as rotary embeddings, and use many heads so that different heads can specialise in different relationships such as syntax, coreference or copying.

Sampling beyond temperature

APIs also expose nucleus sampling, usually called top-p. Instead of reshaping the whole distribution, it trims the unlikely tail and samples only from the most probable tokens that together cover probability p.

How it works

top_p_sample sorts tokens by probability, accumulates the totals, and keeps the smallest set whose cumulative probability reaches p. Everything outside that nucleus is discarded and the survivors are renormalised before sampling. Compared with a fixed top-k, the nucleus adapts: when the model is confident it keeps one or two tokens, and when it is uncertain it keeps many. In practice change either temperature or top-p, not both, and keep both low for extraction and classification.

How a chat model is built, and why inference is expensive

A chat model is made in stages. Pre-training trains a transformer to predict the next token over trillions of tokens of text and code, and this is where nearly all knowledge and capability come from. Supervised fine-tuning then trains it on curated pairs of instructions and good responses so it behaves like an assistant. Preference optimisation, through reinforcement learning from human feedback or simpler methods such as DPO, nudges it toward answers that people or reward models rank higher. Reasoning models add reinforcement learning on problems with checkable answers, which teaches them to spend extra tokens thinking before they reply.

At inference time, the model generates one token at a time. To avoid recomputing attention over the whole prompt for every new token, servers keep a KV cache of the keys and values of earlier tokens, so each step is cheap, but the cache grows with context length and dominates GPU memory in long conversations. Quantization stores weights in 8 or 4 bits instead of 16, cutting memory and cost at a small quality loss, and batching serves many users on one GPU. These details explain the pricing you see: input tokens are cheaper than output tokens, long contexts cost more, and smaller models are much faster.

Your first AI call

How it works

load_dotenv copies the entries of .env into the process environment, and OpenAI() reads OPENAI_API_KEY from there, so the secret never appears in source code. MODEL is a variable on purpose: model names are retired and replaced regularly, and one constant turns an upgrade into a one-line change.

The messages list is the whole conversation, because the API is stateless. The system message sets role and rules, user messages are the questions, and assistant messages are earlier replies that you send back to simulate memory. A temperature of 0.3 keeps the answer focused. The reply lives at response.choices[0].message.content, where choices is a list because the API can return several candidates. response.usage reports prompt and completion tokens, numbers worth logging from day one because they are your cost.

Version note

The model name above is an example. Models are retired and replaced often. Before you build, open the OpenAI models page and pick a current, low-cost model for practice.

Streaming: show words as they arrive

How it works

With stream=True the call returns an iterator instead of a finished response, and the server sends the answer as a series of small chunks over one open connection. Each chunk carries a delta, the new fragment of text, which can be empty on the first and last chunks, so the if piece guard skips those.

Printing with end="" and flush=True avoids line breaks and forces the text to appear at once instead of waiting in a buffer. Streaming does not make generation faster, but it shortens the time to first token that a user perceives, which is what makes a chat interface feel responsive.

Get JSON back, not prose

Programs need predictable data. Ask for JSON and parse it.

How it works

The prompt names the exact keys you want and contains the word JSON, which JSON mode requires. The response_format argument constrains the model to emit syntactically valid JSON, and json.loads turns that text into a Python dictionary.

Valid syntax is not the same as correct content. The model can still omit a key or invent a value, so production code validates the result, for example with a Pydantic model, and handles failure explicitly. When you need stronger guarantees, look at the structured outputs feature, which enforces a full JSON Schema.

The newer Responses API

OpenAI also offers the Responses API, a simpler call that also supports built-in tools. The basic form is shorter. Learn Chat Completions first because the many tutorials and libraries you will meet use it, then try this.

How it works

The Responses API collapses the message list into two arguments. instructions plays the part of the system message, and input can be a plain string for a single turn or a list of messages. output_text joins the text parts of the result into one string.

The reason to learn it is that it also supports built-in tools and server-side conversation state, which reduces the plumbing you write yourself. The chat-completions pattern remains the one that most libraries and tutorials still use, so you need both.

Production-grade calls: retries, timeouts, concurrency

In a demo a call either works or you rerun it. In production calls fail for ordinary reasons: rate limits, dropped connections and slow responses. The official SDK already retries a couple of times by default, but you should understand the pattern so you can control it.

How it works

Only transient errors are retried: a rate limit, a lost connection or a timeout. A bad request or an invalid key will fail identically every time, so retrying it only wastes time. The wait doubles after each failure, which is exponential backoff, and the random jitter added to it stops many clients from retrying at the same instant and overloading the service again. The final attempt re-raises the error so that your monitoring sees it instead of the failure being swallowed. Setting timeout on the client guarantees that no call can hang forever.

How it works

Model calls spend almost all their time waiting on the network, so running them concurrently gives a large speed-up. AsyncOpenAI provides awaitable calls, asyncio.gather starts all the tasks and returns their results in the original order, and the semaphore caps how many are in flight so that you stay under your rate limit. Classifying a thousand items this way takes a fraction of the time of a plain loop.

Costs deserve the same engineering attention. Count tokens before sending, trim history, cap the output length, put stable instructions at the beginning of the prompt because providers can reuse the computation for a repeated prefix, and route easy tasks to a smaller model while keeping the larger one for hard cases. Log token usage per feature so that you notice when one prompt change doubles your bill.

Few-shot prompting in code

Giving examples teaches the model your exact format. Here it learns to label the mood of a message.

How it works

A few-shot prompt teaches by demonstration. The system message defines the label set and the output format, each user and assistant pair is a worked example that the model imitates, and the last user message is the real input. The examples also fix the format, one upper-case word, which lets your code compare the output directly with an expected label.

Temperature 0 removes sampling noise from classification. Choose examples that cover hard edge cases rather than obvious ones, and keep their label balance realistic, because models are sensitive to both the order and the proportion of examples.

Habits that improve results

  • Say what to do, not only what to avoid.
  • Put long documents in clearly marked sections such as Document: and Question:.
  • Ask for step-by-step reasoning on hard problems, then ask for a short final answer.
  • Change one thing at a time and compare outputs on the same five test inputs. This is the start of evals.
Security

Prompt injection is when text the model reads (a web page, an email) contains hidden instructions like "ignore your rules". Treat all outside text as untrusted data. Never let a model run powerful actions on instructions it found in a document without a check.

LangChain

LangChain gives you building blocks for LLM apps: prompt templates, model wrappers, parsers and tools that snap together.

  • Prompt templates
  • Chains with |
  • Structured output
  • Chat memory
Why use it

You can call OpenAI directly (chapter 5). LangChain helps when you want to swap models easily, reuse prompt templates, connect tools and document loaders, or build agents. Start with the direct API so you understand what LangChain is doing for you.

Your first chain

How it works

A ChatPromptTemplate is a function from a dictionary to a list of messages, with the names in curly braces acting as slots. The pipe operator joins components that share a common interface called a Runnable, so prompt | llm | StrOutputParser() means: format the prompt, call the model, and extract the plain string from the message object.

This composition style is the LangChain Expression Language. Its value is that every chain automatically gains invoke, batch for running many inputs in parallel, and stream, with no extra code. Because the model is just another component, you can swap ChatOpenAI for another provider's class and leave the rest of the chain untouched.

Structured output with Pydantic

Describe the shape of the answer as a Python class. LangChain makes the model fill it in and hands you a real object.

How it works

The Pydantic class is a typed contract. Each field has a type that is validated at run time, and each Field(description=...) is passed to the model as part of the schema, so clear descriptions directly improve output quality.

with_structured_output binds that schema to the model, using the provider's native tool-calling or structured-output feature underneath, and returns an instance of your class instead of text. So plan.steps is a real Python list, and a malformed answer raises an error rather than flowing silently into the rest of your program, which is exactly the property you want in an automated system.

Chat with memory

LLMs forget between calls. Memory means you store the past messages and send them again each time. Here is the plain version, which is what every framework does underneath.

How it works

Language models are stateless, so memory is only the practice of sending earlier messages again. The history list holds typed message objects, and every call to chat appends the user's turn, sends the entire list, and appends the reply. The second question works only because the first exchange is still in the list.

This design has a cost: the prompt grows each turn, so latency and price grow with it. Real applications trim the oldest turns, summarise them into a short note, or store facts in a database and retrieve only the relevant ones, which is the long-term memory pattern that agents use.

Version note

LangChain changes quickly. Import paths and helper functions move between versions. If a snippet fails with an import error, check the LangChain docs for your installed version with pip show langchain.

RAG: chat with your data

Retrieval-Augmented Generation looks up relevant text first, then asks the model to answer using only that text. It is the most common real-world LLM pattern.

  • Embeddings
  • Similarity search
  • Grounded answers

The idea in four steps

1 Split

Chunk documents

Cut text into pieces of a few hundred words.

2 Embed

Turn text into numbers

Each chunk becomes a vector that captures meaning.

3 Search

Find the closest chunks

Embed the question and compare to every chunk.

4 Answer

Ask with context

Paste the best chunks into the prompt and ask.

RAG from scratch in 40 lines

No vector database yet. Just embeddings and maths, so you see exactly how it works.

How it works

The program has two phases. In the indexing phase, embed sends text to an embedding model, which returns one high-dimensional vector per text, and the vectors for all documents are computed once and kept in doc_vectors. A real system stores them in a vector database.

In the query phase the question is embedded the same way and compared with every document using cosine similarity. The line with @ computes a dot product divided by the product of the vector lengths, so only the direction of each vector matters. argsort, a reversal and a slice pick the k highest scores. The retrieved text is then placed in the prompt with an instruction to answer from it alone and to admit when the answer is missing, which is the mechanism that suppresses hallucination.

Notice that the question about a fine never uses the words late return, yet retrieval succeeds. Embeddings place texts with similar meaning close together regardless of exact wording, which is the whole point of semantic search.

Making it production-ready

  • Use a vector database (Chroma, FAISS, pgvector, Pinecone, Qdrant) once you have more than a few thousand chunks.
  • Chunk with overlap so a sentence is not cut in half.
  • Return the source of each chunk so answers can show where they came from.
  • Test with 20 real questions and check retrieval first. Most bad RAG answers come from retrieving the wrong chunks.

Advanced retrieval

The from-scratch version above works on four sentences. Real corpora expose the weak points, and most RAG quality problems are retrieval problems, not generation problems. Three techniques give the largest gains: chunking that respects structure, hybrid search that combines meaning with keywords, and a measurement loop so you know whether a change helped.

How it works

Fixed-size windows with overlap are the simplest chunker. The overlap means a sentence that straddles a boundary still appears whole in at least one chunk. Storing the start offset with each chunk lets you cite where an answer came from. Better chunkers split on headings, paragraphs or sentences, keep a table or code block together, and attach metadata such as the document title, section and date, which you can later use to filter results. Chunk size is a trade-off: small chunks match precisely but lose context, large chunks keep context but dilute the embedding and waste prompt tokens, so test several sizes against your own questions.

How it works

Embeddings are strong at paraphrase but can miss exact strings such as error codes, product names or section numbers, where classic keyword ranking such as BM25 shines. Hybrid search runs both and merges the lists. Reciprocal rank fusion does this without needing comparable scores: each document earns 1 / (k + rank) from every list it appears in, so documents ranked well by both rise to the top. In the example d1 and d3 win because both retrievers agree on them. A reranker, usually a cross-encoder model that reads the question and a candidate together, is often added as a final step to reorder the top twenty or so results before the best few go into the prompt.

How it works

This is the measurement loop that turns RAG from guesswork into engineering. You write twenty to fifty real questions and, for each, record which chunk contains the answer. hit_rate then reports how often the right chunk is in the top k results, and you rerun it after every change to chunk size, embedding model or search method. Check retrieval before you look at generation, because if the right text never reaches the prompt, no prompt can fix the answer. Later add generation checks, for example whether each claim in the answer is supported by the retrieved text, which is called faithfulness.

Other techniques worth knowing are query rewriting, where a model turns a vague question into a better search query, filtering by metadata before the vector search, and, for small corpora, skipping retrieval entirely and placing the whole document in a long context window, which can be simpler but costs more per call.

Agentic AI

An agent is an LLM in a loop that can choose tools, use their results, and decide what to do next until the job is done.

  • Tool calling
  • Agent loop
  • LangChain agents
  • Safety

Chatbot vs agent

Chatbot

Answers once

You ask, it replies. It cannot look anything up or take action.

Agent

Plans and acts

It decides to search, calculate, read a file or send a request, checks the result, and continues.

The core loop has four parts: think (decide what is needed), act (call a tool), observe (read the tool result), repeat or finish. Researchers call this pattern ReAct, short for reason and act.

Build an agent with no framework

This is the most important code in the book. Once you understand this loop, every agent framework makes sense.

How it works

Everything an agent does reduces to this loop. The tools are ordinary functions, and tool_specs describes them to the model in JSON Schema: a name, a description and typed parameters. The model never sees your code, only that description, so a precise description is the most important thing you write for a tool.

On each pass the model either returns plain content, meaning it is finished, or returns tool_calls, a structured request naming a function and its JSON arguments. Your program, not the model, executes the function. It parses the arguments, calls the matching entry in TOOLS, and appends the result as a message with role tool and the same tool_call_id, which is how the API links answers to requests. The assistant message must be appended first, because a tool result has to follow the request that caused it.

On the next iteration the model reads the result and decides again. For this question it typically asks for the word length, then for the sum, then answers in text. The range(5) cap is a hard safety limit, because a confused agent can otherwise loop indefinitely and spend money. This version runs calls sequentially and trusts the model's arguments; a production version validates them and may run independent calls in parallel.

The same idea in LangChain

The framework hides the loop. You list tools and it runs think, act, observe for you.

How it works

The @tool decorator reads the function's name, type hints and docstring and builds the same JSON Schema description that you wrote by hand in the previous example. That is why the docstring is not optional: it is the model's only documentation for the tool.

create_agent assembles the model, the tools and the system prompt into the think, act, observe loop and manages the message history. The model is named as a provider:name string. invoke takes and returns a dictionary with a messages list, so the final answer is the content of the last message. What you gain over the hand-written loop is streaming, retries, structured output and hooks for middleware. What you lose is visibility, so when something goes wrong, remember that underneath it is exactly the loop you wrote above.

Version note

Agent helpers have been renamed in past LangChain releases. If create_agent is not found, upgrade with pip install -U langchain or check the docs. For complex flows with branching and saved state, look at LangGraph, the sister library for stateful agents.

Agent safety checklist

Cap the number of steps. Give tools the least power they need (read-only first). Ask a human to approve anything that sends, pays, deletes or publishes. Log every tool call. Treat tool outputs as untrusted text. An agent that can act is a program with real consequences.

Also learn about MCP, the Model Context Protocol. It is an open standard for plugging tools and data sources into AI apps, so one tool server can work with many different assistants.

LangGraph: agents as state machines

A single loop is fine for simple tasks. When you need branches, retries, checkpoints or a human approval step, model the workflow explicitly as a graph. LangGraph represents it as nodes (functions that read and update a shared state) connected by edges, some of which are conditional. The example below implements the reflection pattern: write an answer, have a reviewer critique it, and loop back until the reviewer approves or a retry limit is reached.

How it works

The State class is the single source of truth that every node reads and writes. A node is a plain function that receives the state and returns only the keys it wants to update, and LangGraph merges that update into the state. write drafts an answer and counts the attempt, and review asks the model to act as a critic, which often catches errors that the first pass missed.

The interesting part is route, a conditional edge: it inspects the state and returns a label that the mapping translates into the next node, either the end or back to write. The retry counter is a guardrail, because a reflection loop without a limit can cycle forever. Compared with the earlier hand-written loop, the control flow is now visible and testable as a diagram, and graphs of this kind can be paused for human approval and resumed from a saved checkpoint, which is how long-running agents are made reliable.

Designing agents that you can trust

Agents fail in ways ordinary software does not, so design for failure. Give each tool the minimum privilege it needs and prefer read-only tools until an action is proven safe. Validate every tool argument in code, never trusting the model's output, and treat tool results as untrusted text that may contain injected instructions. Put a hard cap on steps, tokens and money per task. Require human approval for irreversible actions such as sending, paying, deleting or publishing.

Evaluate agents as you would any system, but measure the trajectory as well as the final answer: did it choose the right tool, with correct arguments, in a reasonable number of steps, at an acceptable cost? Keep a fixed set of tasks with known good outcomes, run them after every prompt, tool or model change, and track success rate, average steps and cost per task over time. When a framework hides the loop, log each tool call yourself so that you can replay failures.

A daily digest pipeline

The script reads a text file, asks the model to summarise it, and saves a dated Markdown file. Same pattern works for emails, news, tickets or meeting notes.

How it works

The script is built to run unattended. Reading the input path from sys.argv[1] keeps the file name out of the code, so the same script serves any source. The timeout=60 argument matters more than it looks: without it a stalled network call can hang a scheduled job for hours.

The output path combines a folder with today's date, which gives one file per day and never overwrites yesterday's result. mkdir(exist_ok=True) makes the first run and every later run behave the same, a property called idempotence that automation should have wherever possible. The if __name__ == "__main__" guard lets other modules import summarize without triggering a run, which makes the function testable.

Schedule it

Option A: cron on a Linux or Mac machine that stays on. The five fields are minute, hour, day, month, weekday. This runs at 8:00 every morning.

Option B: GitHub Actions, free for small projects and no server needed. Save this as .github/workflows/digest.yml and add your key under repository Settings, Secrets and variables, Actions, named OPENAI_API_KEY.

How it works

GitHub evaluates schedules in UTC, and India is five and a half hours ahead, so 02:30 UTC fires at 08:00 IST. Adding workflow_dispatch gives you a manual Run button, the fastest way to test a workflow without waiting for the clock.

The secret is read from the repository's encrypted store through the secrets context and injected as an environment variable for that single step, so the key never appears in the repository or the logs. Scheduled workflows can be delayed during busy periods and are disabled automatically after long inactivity on a repository, so a business-critical job needs monitoring.

Expose your AI as an API

A webhook endpoint lets other tools call your AI. This one classifies support messages. Install pip install fastapi uvicorn, save as server.py, run uvicorn server:app --reload, and open /docs in your browser for a free test page.

How it works

FastAPI turns type hints into behaviour. The route decorator binds the function to POST /classify. Because the parameter is annotated with the Pydantic class Ticket, FastAPI parses the JSON body, validates it, rejects malformed requests with a clear error, and generates interactive documentation at /docs.

The returned dictionary is serialised to JSON. This is the shape of most AI backends: a thin, validated web layer around one or more model calls. Before exposing it publicly, add authentication, input length limits and rate limiting, because every request costs you money.

Make automation trustworthy

  • Retries. Networks fail. Retry with a wait that grows (1s, 2s, 4s) and stop after a few tries.
  • Logging. Save inputs, outputs, token counts and errors so you can debug at 8 am the next day.
  • Budget limits. Set a monthly spend cap in your OpenAI account and a maximum steps value in agents.
  • Human approval. Draft emails and actions for review before anything is sent automatically.
  • Evals. Keep 20 sample inputs with ideal outputs. Run them after every prompt or model change.

Production LLM engineering

The gap between a demo and a product is evaluation, observability, caching, safety and cost control. This chapter covers the practices that senior AI engineers are hired for.

  • Evals
  • Observability
  • Caching
  • Fine-tuning and LoRA
  • Security

The shape of a production request

A reliable LLM feature is a pipeline of small, testable stages around the model call, not a single call.

Input checks→Retrieve context→Model call→Validate output→Log and meter

Input checks limit length and strip or flag suspicious content. Retrieval supplies the facts. The model call has a timeout and retries. Output validation checks the schema, rejects unsafe or unsupported content and can trigger a repair attempt. Logging records the prompt version, latency, tokens and outcome. Each stage can be tested and improved separately, and each is a place where failures are caught before a user sees them.

Evals: tests for non-deterministic software

Prompts are code, and code needs tests. An eval is a fixed set of inputs with expected outcomes that you run on every change. Start with exact-match checks where an answer is a label, then add model-graded checks for open-ended answers.

How it works

CASES is the golden set: realistic inputs paired with the answer you consider correct. run_eval runs the real function on each case, records pass or fail, prints the failures so you can read them, and returns one number you can track from commit to commit. Wire it into your continuous integration so that a prompt edit which breaks previously working cases is caught before release. A good set grows from production: whenever a user finds a failure, add that input as a new case.

judge shows the model-graded variant, often called LLM-as-judge, where a second call scores an open-ended answer against a rubric. It scales human review, but it has biases, for example favouring longer answers or its own style, so calibrate it by comparing its scores with a sample of human ratings, use a clear rubric, and prefer pairwise comparisons for close calls.

Observability: know what your system did

When a user says the assistant gave a strange answer, you need to reconstruct exactly what happened. Log every call with a request id, the prompt version, model name, latency, input and output token counts, and the result of validation. Mask personal data before storing logs.

How it works

The wrapper records one structured JSON line per call, which any log tool can search and chart. try, except and finally together guarantee that a record is written whether the call succeeds or fails, and the exception is re-raised so callers still see the error. Recording the prompt version lets you compare quality and latency before and after a change, and the request id lets you tie a user complaint to one exact call. Extend the record with token counts from response.usage and your cost per feature becomes a query rather than a surprise. Dedicated tracing tools add a visual timeline of each step in a chain or agent, but the habit of structured logging comes first.

Caching and latency

The cheapest call is the one you do not make. Many applications see the same requests repeatedly, such as identical classification inputs or repeated FAQ questions. An exact-match cache keyed on a hash of the model, parameters and messages is simple, safe and effective, and only applies when the output is meant to be repeatable, so use it with temperature 0.

How it works

The key is a SHA-256 hash of the serialised model and messages, with sort_keys=True so that identical content always yields identical text. A hit returns instantly and costs nothing, and the function also reports whether it was a hit, which you should count to measure the saving. In production the dictionary becomes Redis or a database table with an expiry time, so stale answers age out. A semantic cache goes further by matching questions that mean the same thing using embeddings, at the price of occasionally returning an answer to a slightly different question, so set a strict similarity threshold. For latency, also stream responses, run independent calls in parallel, shorten prompts and send easy requests to smaller models.

Fine-tuning, LoRA and open models

Before you fine-tune, exhaust the cheaper options. The decision is usually clear once you ask what is missing.

ProblemBest first toolWhy
Model lacks your private or fresh factsRAGFacts change; retrieval updates instantly and can cite sources
Output format or tone is inconsistentBetter prompt, examples, structured outputCheap and reversible
A narrow task needs consistent behaviour at low cost and latencyFine-tune a smaller modelBakes the pattern in so prompts get shorter
Data cannot leave your serversOpen-weight model on your own hardwareFull control, but you operate it

Full fine-tuning updates every weight and needs large GPUs. LoRA, low-rank adaptation, freezes the original weights and learns a small update expressed as the product of two thin matrices, which can be orders of magnitude smaller than the original matrix. That makes fine-tuning feasible on a single GPU, and the small adapter can be swapped in and out. Combined with 4-bit quantization of the base model, a method known as QLoRA, even large open models become trainable on modest hardware. Open models are run most easily through the Hugging Face libraries.

How it works

pip install transformers torch first. The pipeline helper downloads the model weights from the Hugging Face Hub on the first run, loads them, and wraps tokenization and generation into one callable. A half-billion-parameter model is small enough to run on an ordinary laptop CPU, so it is a good way to see how an open model behaves, how fast it is, and how its quality compares with a hosted model. do_sample=False makes the output deterministic by always taking the most likely token, the equivalent of temperature 0. Open models are the route to private deployment, but they shift the operational work, such as serving, scaling, updates and safety, onto you.

Security and safety, briefly

Treat the model as an untrusted component. Prompt injection, where text that the model reads contains instructions, cannot be fully prevented by wording, so limit the damage instead: separate untrusted content from instructions, give tools least privilege, require approval for consequential actions, and never place secrets in prompts. Validate outputs before acting on them, filter personal data from logs, and rate-limit users so that one account cannot drain your budget. For systems that reach real users, add moderation checks and keep a record of what the system did and why, because you will be asked.

Causal maskBlocks attention to future tokens so the model predicts the next token fairly.
Feed-forward networkThe per-token layer after attention, holding much of the model's parameters.
Residual streamThe running vector that each layer reads from and adds to.
RMSNormA cheaper normalisation used in many modern LLMs.
Decoder-only transformerThe architecture of GPT-style and most chat models.
Pre-trainingLearning from huge text by predicting the next token.
PerplexityA measure of how surprised the model is by text. Lower is better.
Scaling lawsEmpirical rules linking loss to model size, data and compute.
Mixture of expertsMany expert sub-networks with a router that uses only a few per token.
FlashAttentionA memory-efficient way to compute attention that is much faster on GPUs.
KV cacheStored keys and values of past tokens that make generation fast.
Speculative decodingA small model drafts tokens and a large one verifies them to speed generation.
QuantizationStoring weights in fewer bits to cut memory and cost.
DistillationTraining a small model to imitate a large one.
SFTSupervised fine-tuning on instruction and answer pairs.
RLHF and reward modelTuning with human preferences, using a model that scores answers.
DPODirect preference optimisation: learns from preference pairs without a separate reward model.
LoRA and QLoRATraining small low-rank adapters instead of all weights, optionally on a 4-bit base model.
Chain-of-thought and reasoning modelsPrompting or training models to work step by step before answering.
Benchmark and contaminationA standard test set, and the problem of test questions leaking into training data.
Alignment and red teamingMaking models behave safely, and attacking them deliberately to find failures.
Multimodal modelA model that handles text, images, audio or video.
